# Feature Specification: Deep-Identification Run History & Wishlist-Eligible Coin of the Day

**Feature Branch**: `354-run-history-and-wishlist-featured-coin`
**Created**: 2026-08-19
**Status**: Draft
**Owner**: Maximus (Lead / Architect)
**Requested by**: Brian DeNicola
**Input**: User description: "1) Persist every completed deep-analysis/deep-identification run and its full details so a user can revisit it later, optionally save its identified item to their wishlist or collection even if they previously changed their mind, and delete their own runs. 2) Include wishlist coins in Coin of the Day eligibility. When the selected item is from the wishlist, clearly mark it as wishlist-origin and generate/cache an AI summary explaining why it would be a good addition to that user's collection. Owned coin behavior must remain intact."

## Context and Scope

Aurearia already has a **fully working Deep Identification pipeline** (specs 344 / 351 / 352 — Implemented). Jobs are represented by `models.DeepIdentificationJob`, `DeepIdentificationArtifact`, `DeepIdentificationEvent`, and `DeepIdentificationProviderRun`; the API surface (list, get, cancel, retry, patch proposal, apply proposal) is already exposed under `/deep-identification/jobs/*`. Today, however:

- Every job carries `ExpiresAt = created_at + 90d`; the janitor (`services/deep_identification_janitor.go` → `runRetentionSweep`) deletes any job past that window regardless of terminal outcome, along with its artifacts. This makes long-term "revisit" impossible.
- There is no user-invoked delete endpoint. Runs disappear only on the timed sweep.
- `DeepIdentificationRepository.ApplyJob` is single-shot: `WHERE applied_at IS NULL`. Users who dismiss a run's proposal and later change their mind cannot save it because subsequent apply calls return `ErrDeepProposalAlreadyApplied`.
- The frontend has `DeepAnalysisPage.vue` (single-job detail) and `useDeepIdentification` composable but no history / list / revisit / delete UX.

Aurearia also has a working **Coin of the Day** pipeline (spec 001 §"Coin of the Day"). `services/coin_of_day_scheduler.go` picks one coin per opted-in user per day via `FeaturedCoinRepository.PickNextCoinID`, whose SQL restricts eligibility to `is_wishlist = 0 AND is_sold = 0`. `FeaturedCoin.Summary` is snapshotted from `buildCoinSummary` (owned-coin narrative fallback chain — no live AI call). The in-app notification and `FeaturedCoinModal` render that cached prose.

This feature makes deep-identification runs a **persistent, revisitable, user-deletable** first-class history object and makes Coin of the Day **source-aware** so wishlist coins are eligible with a distinct, cached "why this belongs in your collection" summary generated by the Python agent. The Python `/deep_identify` and vision-first pipelines (specs 344/351/352) are **unchanged**. Availability observability (spec 353) and Wishlist Search Alerts (spec 337) are **out of scope**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Revisit a completed deep-identification run days later (Priority: P1)

As a collector who ran Deep Analysis on a coin last week and left without saving it, I want to open the same run and see the exact same report, proposal, and reference images so I can decide again — with everything I saw before still intact.

**Why this priority**: This is the core persistence gap. Without it every other story is moot.

**Independent Test**: Complete a Deep Analysis run (`completed` or `partial`). Wait long enough that the current 90-day janitor sweep would have deleted it (simulate by advancing the janitor's clock). Open a new session, list runs, click one, and confirm `report`, `proposal`, obverse and reverse images, and status/`completedAt` are byte-identical to what the run finished with. Hint images are gone.

**Acceptance Scenarios**:

1. **Given** a terminal-completed or terminal-partial run older than 90 days, **When** the janitor's retention sweep runs, **Then** the run row, its obverse/reverse artifact rows, its report JSON, and its proposal JSON are still present; only hint artifacts and streaming events remain subject to their existing shorter retention.
2. **Given** the user opens the run detail view for a historical run, **When** the page loads, **Then** the same `report` + `proposal` + `status` + `appliedCoinId`/`appliedDraftId` shown at completion time are rendered, and the obverse/reverse images fetched via the existing artifact serving path still resolve.
3. **Given** a run in a terminal `failed` or `cancelled` state, **When** 90 days elapse, **Then** existing 90-day expiry may still apply to failed/cancelled runs (they are not "completed"); the UI list clearly labels them and the user may still delete them manually while they exist.

### User Story 2 — Save the identified item to wishlist or collection after previously changing my mind (Priority: P1)

As a collector who dismissed a run's proposal, when I revisit that run later I want to be able to save its identified item to my collection or wishlist without hitting a "already applied" error.

**Why this priority**: Brian's binding requirement #1: users must be able to save "even if they previously changed their mind." The current single-shot apply blocks this cold.

**Independent Test**: Complete a deep run (intake source), do not apply. Later revisit the run, click "Add to Wishlist" — a new wishlist coin is created and the run records the linkage. Click "Add to Wishlist" **again** on the same run — no duplicate coin is created; the existing linked wishlist coin is returned. Delete the linked wishlist coin from the collection; click "Add to Wishlist" a third time — a new wishlist coin is created and the run's linkage is refreshed to it.

**Acceptance Scenarios**:

1. **Given** a completed intake-source run with no prior apply and target=`wishlist`, **When** the user applies, **Then** a new `Coin` with `IsWishlist=true` is created via the existing allowlisted `applyToWishlist` path and the run's `AppliedCoinID` + `AppliedAt` are set.
2. **Given** a completed run that has already been applied to wishlist and whose `AppliedCoinID` coin still exists, **When** the user applies with the same target=`wishlist`, **Then** the API returns HTTP 200 with the existing linked coin — no new row is created and no error is raised.
3. **Given** a completed run that has already been applied but the linked coin has been deleted, **When** the user applies again with target=`wishlist`, **Then** a new coin is created and the run's linkage is updated in place; `AppliedAt` is refreshed to the latest apply.
4. **Given** a completed saved-coin-source run whose `AppliedCoinID` points at an existing coin, **When** the user re-applies with target=`coin`, **Then** the target coin's allowlisted fields are re-patched (idempotent for identical proposal state) and the run's `AppliedAt` is refreshed. Existing coin history/references are preserved (no destructive replace).
5. **Given** any completed run, **When** the user tries to apply with a target incompatible with `job.Source` (e.g., saved-coin run → wishlist target), **Then** the API rejects with the existing `ErrDeepProposalTargetMismatch` semantics unchanged — this feature does not widen source/target coupling.

### User Story 3 — Delete a run I no longer want (Priority: P1)

As a collector, I want to remove specific historical runs from my history — because they were noisy, private, or simply clutter — without affecting any coin I may have already saved from them.

**Why this priority**: Persistent history without user-initiated pruning is a privacy / clutter regression Brian explicitly ruled out.

**Independent Test**: Complete two runs; save a wishlist coin from run A. Delete run A. Confirm: (a) the wishlist coin still exists in the collection, (b) run A is gone from the history list and its detail endpoint returns 404, (c) run A's obverse/reverse and any surviving hint files on disk are removed, (d) run B is untouched.

**Acceptance Scenarios**:

1. **Given** the user owns a terminal-state run, **When** they call `DELETE /deep-identification/jobs/{id}`, **Then** the API returns 204, the row is removed, all `DeepIdentificationArtifact`, `DeepIdentificationEvent`, and `DeepIdentificationProviderRun` rows for that job are deleted, and the underlying files under the upload dir are unlinked best-effort (matching the existing janitor cleanup path).
2. **Given** the run had `AppliedCoinID` set to an existing `Coin`, **When** the run is deleted, **Then** the `Coin` is **not** deleted or modified. The linkage simply vanishes with the run row. Any journal entry recorded on the coin (via `recordDeepProposalJournalEntry`) is left intact.
3. **Given** a run that is not yet terminal (`queued` or `running`), **When** the user calls `DELETE`, **Then** the API returns HTTP 409 with a message asking them to cancel first. Non-terminal deletion is disallowed to avoid racing the pipeline runner.
4. **Given** a run owned by a different user, **When** any user calls `DELETE` for it, **Then** the API returns 404 (not 403), matching existing `GetJob` owner-scoping semantics — non-ownership must be indistinguishable from "not found".

### User Story 4 — See my run history (Priority: P2)

As a collector, I want a browsable list of my past deep-identification runs so I can find, filter, and revisit them.

**Why this priority**: The `GET /deep-identification/jobs` endpoint already exists and is already exercised. This story mainly formalizes the frontend UX and confirms the list behaves correctly at longer retention windows. Without it users have no discoverability path back to a persisted run.

**Independent Test**: With ten historical runs across statuses (completed, partial, failed, cancelled), open `/deep-identification/history`. Confirm rows appear in reverse-chronological order with status, source (`intake`/`saved_coin`), coin thumbnail (if `saved_coin`) or first artifact thumbnail (if `intake`), and applied-linkage indicator. Verify cursor pagination continues past the current on-screen page.

**Acceptance Scenarios**:

1. **Given** 30 terminal runs, **When** the user opens the history page, **Then** the first 20 render, "Load more" advances the cursor, and total count is available for empty-state discrimination.
2. **Given** a run row, **When** the user clicks it, **Then** the existing `DeepAnalysisPage.vue` opens against the historical `jobId` and renders `report` + `proposal` deterministically from the persisted JSON (no re-streaming).
3. **Given** a run row with `AppliedCoinID` populated and the linked coin still exists, **When** the row renders, **Then** a "Saved to Collection" or "Saved to Wishlist" badge is shown, distinct from unsaved rows.

### User Story 5 — Get a wishlist coin as my Coin of the Day (Priority: P1)

As a wishlist-conscious collector, I want my Coin of the Day to occasionally surface a coin from my wishlist, clearly labeled as such, with a short AI-generated rationale about why it would be a good addition — so the daily prompt helps me plan future acquisitions, not just re-savour what I already own.

**Why this priority**: Brian's binding requirement #2. Delivers immediate product value on top of an already-shipped feature and unlocks the existing wishlist for the daily loop.

**Independent Test**: For a user with 3 owned coins and 2 wishlist coins, run the scheduler five consecutive days. Verify: (a) all five distinct coins appear before any repeats (fair cycle across the combined owned+wishlist pool), (b) each wishlist selection carries `sourceType="wishlist"` and a cached `summary` whose text is distinctly different from the owned-coin fallback and mentions its wishlist-origin framing, (c) the `FeaturedCoinModal` visibly labels wishlist picks and offers "Move to collection" instead of the standard "View coin".

**Acceptance Scenarios**:

1. **Given** a user with owned and wishlist coins, **When** `PickNextCoinID` runs, **Then** the eligible pool is the union of `is_wishlist = 0` and `is_wishlist = 1` coins (both still filtered by `is_sold = 0`), and cycle fairness (never-shown-first, then oldest `last_shown`) is applied over that combined pool.
2. **Given** the picked coin is a wishlist coin, **When** the summary is built at pick time, **Then** the Go scheduler calls the Python agent for a "wishlist rationale" summary, receives a bounded plain-text response, and stores it in `FeaturedCoin.Summary`. `FeaturedCoin.SourceType` is set to `"wishlist"`.
3. **Given** the picked coin is an owned coin, **When** the summary is built, **Then** the existing `buildCoinSummary` fallback chain is used exactly as today; `FeaturedCoin.SourceType` is `"owned"`; no Python call is made.
4. **Given** the Python agent is unavailable, times out, or returns an error, **When** a wishlist coin is picked, **Then** the scheduler falls back to a static wishlist-framed summary derived from `buildCoinSummary` (prefixed with a fixed "From your wishlist —" preamble) and records the fallback in logs; the `FeaturedCoin` is still created and the notification still fires. **The pick is never dropped for AI failure.**
5. **Given** the notification fires, **When** the recipient opens the `FeaturedCoinModal`, **Then** wishlist-origin rows show a "Wishlist" badge and a "Move to Collection" primary action; owned-origin rows behave exactly as today (title, summary, "View coin"). Notification `type` remains `coin_of_day` and `referenceId` still points at the `FeaturedCoin.ID` — backward-compatible.
6. **Given** the user has opted out of wishlist inclusion (per-user setting), **When** the scheduler picks for them, **Then** eligibility falls back to owned-only exactly as today; behavior is byte-identical to the current shipping code.

---

### User Story 6 — Bounded, non-destructive retention that never eats a wishlist wait (Priority: P3)

As Brian, I want run history to stay useful without unbounded DB growth, but I never want automatic deletion of a completed run the user might still act on.

**Why this priority**: Product / operational hygiene. Non-terminal-completed runs (failed/cancelled) may still expire on the current 90-day janitor window; terminal-completed and terminal-partial runs are retained indefinitely until the user explicitly deletes them.

**Independent Test**: Manually set `ExpiresAt` on a `completed` job to the past. Run the janitor sweep. Confirm the job is untouched. Do the same on a `failed` job — confirm it is expired and cleaned exactly as today.

**Acceptance Scenarios**:

1. **Given** a `completed` or `partial` terminal job, **When** any janitor sweep runs, **Then** `ExpiresAt` is ignored (or was cleared at settle-time to a sentinel far-future / NULL) and no delete occurs.
2. **Given** a `failed` or `cancelled` terminal job past `ExpiresAt`, **When** the janitor runs, **Then** existing cleanup semantics apply exactly as today (row + artifacts + files deleted).
3. **Given** a queued or running job stuck past its heartbeat/stale window, **When** the janitor's recovery sweep runs, **Then** existing `RecoverStaleJobs` semantics apply exactly as today (settled to `failed:stale_restart`).

## Functional Requirements

### Run persistence & lifecycle

- **FR-001**: Terminal-completed and terminal-partial deep-identification runs MUST be retained indefinitely — the janitor's ExpiresAt-based deletion path MUST skip them.
- **FR-002**: Failed and cancelled terminal runs retain the existing 90-day retention window; this feature does not change their expiry.
- **FR-003**: Non-terminal runs (queued, running) continue to be recovered by the existing stale-recovery path; nothing about the runtime pipeline changes.
- **FR-004**: `DeepIdentificationJob.ExpiresAt` MAY be `NULL` when the row is retained indefinitely; the janitor's `ListExpiredJobIDs` query MUST treat `NULL` as "never expires". The AutoMigrate change to make the column nullable MUST be additive-only (no destructive DDL, no data loss).
- **FR-005**: Streaming event pruning (`PruneEventsBefore`) semantics are unchanged — events are ephemeral progress signal, not history evidence. History detail renders from `ReportJSON` + `ProposalJSON` + artifacts, never from events.
- **FR-006**: Hint artifacts remain ephemeral and are still deleted at terminal-transition or by the defensive backstop, exactly as today. **Only obverse and reverse artifacts are retained** as revisitable evidence.

### Re-apply idempotency

- **FR-007**: `POST /deep-identification/jobs/{id}/apply` MUST allow multiple invocations on the same terminal-completed / terminal-partial job.
- **FR-008**: If the run already has `AppliedCoinID` set and (a) the target argument matches the previously applied target and (b) the linked `Coin` still exists and is owned by the caller, the API MUST return HTTP 200 with a payload referencing the existing `AppliedCoinID`. No new coin, no new draft, no journal entry.
- **FR-009**: If `AppliedCoinID` is set but the linked coin no longer exists (or is not owned by the caller), the apply MUST be re-executed as if it were fresh; `AppliedCoinID` and `AppliedAt` are updated to the new result.
- **FR-010**: If `target="draft"` and a prior `AppliedDraftID` still exists and has not expired, the API MUST return 200 with the existing draft; if the draft has expired or been consumed, a new draft is created and `AppliedDraftID` is refreshed.
- **FR-011**: `target="coin"` re-apply against an existing owned saved-coin target MUST be a re-patch through the same `applyToCoin` allowlisted-field path. Catalog references are appended additively (existing `AppendForCoin`), never replaced. `AppliedAt` is refreshed.
- **FR-012**: Source/target coupling (`intake` ↔ `draft`/`wishlist`, `saved_coin` ↔ `coin`) remains **unchanged**. `ErrDeepProposalTargetMismatch` semantics are preserved.

### User delete

- **FR-013**: `DELETE /deep-identification/jobs/{id}` (new endpoint, JWT-protected, owner-scoped) MUST hard-delete the job row, all its `DeepIdentificationArtifact`, `DeepIdentificationEvent`, and `DeepIdentificationProviderRun` rows, and unlink any files on disk under `cfg.UploadDir` best-effort. Return 204 on success.
- **FR-014**: Delete MUST be permitted only for terminal-state jobs. Non-terminal (queued/running) returns HTTP 409 with a message directing the user to cancel first.
- **FR-015**: A previously-applied coin (`AppliedCoinID`) MUST NOT be deleted or modified as a side effect of run deletion. Coin-side journal entries recorded during apply are preserved.
- **FR-016**: Delete MUST NOT be permitted across users; non-ownership behaves as 404, mirroring `GetJob`.
- **FR-017**: Delete MUST be idempotent at the file-unlink layer — a missing file MUST NOT fail the request. All DB deletions MUST occur in a single transaction; on transaction failure no rows are removed.

### List/detail

- **FR-018**: The existing `GET /deep-identification/jobs` list endpoint MUST continue to return history in reverse-id order and MUST include a new response field `appliedCoinExists: bool` (true when `AppliedCoinID` resolves to an existing owned coin) to drive the "Saved to Collection/Wishlist" badge cheaply without a second round-trip.
- **FR-019**: The existing `GET /deep-identification/jobs/{id}` detail endpoint MUST continue to render terminal jobs with their persisted `report` + `proposal` regardless of age. No behavior change for non-terminal jobs.
- **FR-020**: A dedicated frontend route (e.g. `/deep-analysis/history`) MUST list terminal runs with cursor pagination and support drill-in to the existing `DeepAnalysisPage.vue` (already keyed by `jobId`) and to the new delete action.

### Coin of the Day — wishlist eligibility

- **FR-021**: `FeaturedCoin` MUST gain a `SourceType` column with values `"owned"` (default) and `"wishlist"`. Existing rows migrate as `"owned"`. The AutoMigrate change is additive; no destructive DDL.
- **FR-022**: `FeaturedCoinRepository.PickNextCoinID` MUST widen its eligible pool to include `is_wishlist = 1` coins (still excluding `is_sold = 1`) when the user's `CoinOfDayIncludeWishlist` setting is enabled.
- **FR-023**: Per-user opt-out setting `User.CoinOfDayIncludeWishlist` MUST default to `true`. When `false`, eligibility falls back to `is_wishlist = 0` — behavior byte-identical to today.
- **FR-024**: Cycle fairness MUST be preserved over the combined pool: never-shown-first, then oldest `MAX(featured_at)`, then id — the same three-key sort already used, unchanged in structure.
- **FR-025**: When the picked coin is a wishlist coin, the scheduler MUST call the Python agent (new endpoint on the agent service, proxied through `agent_proxy.go`) to generate a bounded plain-text "why this belongs in your collection" summary. The response MUST be sanitized and stored in `FeaturedCoin.Summary`.
- **FR-026**: The wishlist-summary Python endpoint MUST be **stateless** (per Principle I / agent architecture), receive coin metadata (name, era, category, denomination, ruler, mint, existing analyses/notes), user context (username or display name for tone only — never sensitive PII), and an AI-provider hint. It MUST return a single short paragraph (soft cap 500 chars) and MUST NOT invent facts about the coin's provenance, price, or history not present in the input.
- **FR-027**: On Python agent failure, timeout, or feature disablement, the scheduler MUST fall back to a static wishlist-framed summary derived from the existing `buildCoinSummary` chain, prefixed with a fixed preamble (e.g. `"From your wishlist — "`). **The pick is never dropped** for AI failure.
- **FR-028**: Owned-coin path — including `buildCoinSummary`, notification content, and modal behavior — MUST remain byte-identical to today.

### Coin of the Day — surfacing & modal

- **FR-029**: `NotificationService.NotifyCoinOfDay` continues to create `type="coin_of_day"` with `ReferenceID` pointing at `FeaturedCoin.ID`. **Backward compatibility is mandatory** — no notification consumer changes.
- **FR-030**: The `FeaturedCoin` JSON payload MUST include `sourceType`. The Vue `FeaturedCoinModal` MUST show a "Wishlist" badge when `sourceType === "wishlist"` and offer a primary action to move the coin to the collection (clear the `IsWishlist` flag via existing coin-update path). Owned-source modals render unchanged.
- **FR-031**: The wishlist-move primary action MUST route through the existing coin-update service (not a new endpoint), reusing existing owner scoping and validation.

## Non-Functional Requirements

- **NFR-001**: Adding `SourceType` and nullable `ExpiresAt` MUST NOT break existing `go test ./...` or migration regression tests. Additive DDL only.
- **NFR-002**: Retention change MUST NOT introduce O(N) scans of historical rows on hot paths. List queries still use the existing `idx_deep_jobs_user_status_created` index; ExpiresAt lookup uses the existing `idx_deep_jobs_expires` index (nullable indexed columns are supported by SQLite).
- **NFR-003**: Wishlist summary generation MUST have a bounded timeout (default 10s) so a stalled agent never blocks a `runCycleWithTrigger` iteration for the whole cycle.
- **NFR-004**: Wishlist summary calls happen sequentially inside the existing per-user loop and MUST be capped at one call per pick — no batch fan-out, no repeated calls per user per day.
- **NFR-005**: All new endpoints MUST comply with Principle V — generic error messages, no leakage of AppliedCoinID for other users, no leakage of file paths, no leakage of AI provider identifiers to clients.

## Non-Goals

- No changes to the Python `/deep_identify` pipeline, vision-first orchestration (spec 351), or structured-results contract (spec 352).
- No new AI provider integrations; wishlist summary uses whichever provider the user has already selected (Anthropic or Ollama).
- No changes to Wishlist Search Alerts (spec 337), Availability Runs (spec 353), or auction-lot subsystems.
- No cross-user visibility of runs. History remains strictly per-owner, matching all existing DeepIdentification endpoints.
- No admin surface for browsing/deleting user runs. Admin observability (`/admin/deep-identification/observability`) is untouched.
- No re-streaming of SSE events for historical runs — persisted `ReportJSON` + `ProposalJSON` are the source of truth.

## Success Criteria

- **SC-001**: 100% of new terminal-completed runs are retrievable at day 91 after their creation date — no auto-deletion.
- **SC-002**: A user who "changed their mind" can save a run's identified item exactly once (idempotent) with a single button click; identical clicks return the same coin id.
- **SC-003**: User-initiated delete succeeds atomically or does not occur at all — no partial delete state (row removed but files retained, or vice versa) survives a crash mid-delete.
- **SC-004**: Wishlist coins appear in Coin of the Day rotation at their fair share of the combined pool; the modal visibly distinguishes them.
- **SC-005**: Every `coin_of_day` notification of `sourceType="wishlist"` carries a non-empty `summary`, regardless of Python agent health.
- **SC-006**: Zero regression in owned-coin Coin of the Day behavior: same picks, same summaries, same modal, same notification content given identical inputs.

## Decision Log (in-spec)

- **D1 (Retention)**: Retain terminal-completed and terminal-partial runs indefinitely by nulling `ExpiresAt` at settle-time and having the janitor treat `NULL` as "never expires". Alternative (long-window like 5y) rejected because it still bounds user history arbitrarily and adds no operational benefit.
- **D2 (Re-apply idempotency)**: Idempotency is per (job, target, linked-coin-existence). Not per timestamp, not per proposal hash. Rationale: matches user mental model — "save this thing" — and avoids proposal-diff heuristics that could silently mutate coins.
- **D3 (Delete cascade)**: Deleting a run does NOT delete an already-created coin. Rationale: user's collection is sacrosanct. Linkage vanishes with the run; coin persists standalone.
- **D4 (Delete guard)**: Non-terminal jobs cannot be deleted — user must cancel first. Rationale: avoids racing the pipeline runner and the broker; matches the existing "cancel then settle" state machine.
- **D5 (List badge)**: List endpoint returns `appliedCoinExists` server-side (cheap `EXISTS`) rather than forcing the frontend to fetch each linked coin. Rationale: minimal, proportional (Principle IV).
- **D6 (Wishlist eligibility)**: Combined-pool cycle rather than separate wishlist round-robin. Rationale: same fairness algorithm, single query, natural interleave. Alternative (weighted rotation) rejected as premature tuning.
- **D7 (Wishlist summary boundary)**: All AI generation is on the Python agent; Go proxies. Same architectural rule as every other AI path in Aurearia. No Python code speaks to the DB.
- **D8 (Wishlist summary fallback)**: Fail-safe deterministic fallback with a fixed preamble; never drop a pick. Rationale: user-visible reliability > freshness of AI prose.
- **D9 (Modal CTA)**: "Move to Collection" reuses existing coin-update path (clear `IsWishlist`). No new endpoint. Rationale: Principle IV.
- **D10 (Notification schema)**: Do not change `NotificationType`; add `sourceType` inside the `FeaturedCoin` payload the modal already fetches. Rationale: backward-compatible with any existing consumer.

## Open Questions

- **Q1**: Should we surface a "How often does a wishlist coin appear?" user hint in Settings — e.g. "If you have 10 owned and 5 wishlist, expect ~1 in 3 picks to be from your wishlist"? Assumed **no** (defer) unless Brian requests it; keeps scope tight.
- **Q2**: Should a wishlist-source Coin of the Day silently be re-featured after the user moves it to their collection? Assumed **yes** — once moved it enters the owned pool naturally and the cycle already prefers never-shown coins; no special-case code needed.

## Constitution Alignment

- **Principle I**: All new backend code lives in Handler → Service → Repository → Models. New Python endpoint is stateless and receives all context per-request.
- **Principle IV**: Reuses `DeepIdentificationJob`, `FeaturedCoin`, `agent_proxy.go`, existing notification, and existing coin-update paths. No parallel subsystems.
- **Principle V**: Delete/apply/list are all owner-scoped, 404-on-non-owner. Wishlist-summary Python endpoint receives no secrets and returns bounded plain text.
- **Principle VI**: Frontend history page and modal changes use existing design tokens, chips, and buttons per the design system in `main.css` / `variables.css`.
- **§17 Quality Gate + §21 DoD**: Every task has a tests-first counterpart; DoD checklist enforced at PR time.
